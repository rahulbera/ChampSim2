# Ramulator2 Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Select the legacy or Ramulator2 memory backend at runtime while preserving legacy numerical behavior.

**Architecture:** A non-clocked backend owner exposes the selected memory operable, capacity, and owned statistics. The legacy owner returns its existing controller directly. The Ramulator adapter uses a private C++20 driver behind a C++17 interface, with safe request fragmentation and callbacks.

**Tech Stack:** ChampSim C++17/Make/vcpkg/Catch2; Ramulator 2.1 C++20/CMake/shared library; TOML and native exported YAML.

**Spec:** `docs/superpowers/specs/2026-09-13-ramulator2-design.md`

## Global Constraints

- Root runtime selector: `dram-model = "legacy"` by default; `dram-model = "ramulator2"` selects the native backend.
- Native input: `[ramulator2] config = "path/to/exported.yaml"`.
- Selecting Ramulator rejects legacy `pmem.*` settings. Selecting legacy rejects Ramulator settings.
- Preserve legacy timing, queues, clock conversion, warmup, statistics, and physical-page mapping at one and two cores.
- Preserve the single shared, unbounded LLC-to-memory feeder and one memory operable.
- No dummy legacy controller and no second Ramulator instance for capacity/clock discovery.
- Native source revision: `72427a1bba3771564c4fb0e494ba02242fd1eaa7` (Ramulator 2.1).
- Only the private native translation unit requires C++20. Legacy-only builds require no native dependency.
- Fast warmup bypasses transaction submission while native clocks continue ticking. Phase resets preserve state and pending callbacks. Finalize once after all phases, without a measured drain.
- Fragment cache blocks as needed; never duplicate accepted fragments or return a parent before all fragments complete. Synchronous write callbacks are supported.
- Preserve metadata and `response_requested`; retain core IDs through a native frontend that reports the actual core count.
- Legacy TOML keeps schema 1. Native TOML uses schema 2 and backend-specific counters without invented legacy zeros.
- Record native YAML contents/hash and pinned native revision; validate replayed hashes/revisions.
- Use the user's v2 traces under `/home/rbera/work/tracezoo/champsim/version2.1/spec26` with `--trace-version 2`.
- Commits use `<component>: imperative summary` and no attribution trailers.

## Task 2: Build and validate the native driver

**Files:** Create `inc/ramulator2_driver.h`, `src/ramulator2_driver.cc`,
`test/cpp/src/704-ramulator2-driver.cc`, and `configs/ramulator2/{ddr4,lpddr5}.{py,yaml}`.

**Interfaces consumed:** Task 1 runtime configuration and memory statistics.
**Interfaces produced:** Private native driver shared by the real backend and
deterministic tests. Public types remain C++17-compatible:

```cpp
struct native_memory_statistics {
  // Dotted/escaped component paths plus typed scalar values, owned by the snapshot.
  std::vector<std::pair<std::string,
      std::variant<int64_t, uint64_t, double, bool, std::string>>> values;
  std::string yaml;
};
struct ramulator2_config_record {
  std::string path, hash, revision, yaml;
};
class ramulator2_driver {
public:
  virtual ~ramulator2_driver() = default;
  virtual champsim::chrono::picoseconds clock_period() const = 0;
  virtual champsim::data::bytes size() const = 0;
  virtual std::size_t transaction_bytes() const = 0;
  virtual bool send(bool write, uint64_t address, uint32_t cpu,
                    std::size_t bytes, std::function<void()> done) = 0;
  virtual void tick() = 0;
  virtual void reset_stats() = 0;
  virtual native_memory_statistics statistics() = 0;
  virtual ramulator2_config_record config_record() const = 0;
  virtual void finalize() = 0;
};
std::unique_ptr<ramulator2_driver> make_ramulator2_driver(
    const champsim::runtime_config&);
bool ramulator2_available();
```

Names live in namespace `champsim`. Include guards and includes are required in
actual headers. The `values` representation may be grouped into path-component
vectors if necessary to preserve dots in native keys; document any such change
before Task 4 consumes it.

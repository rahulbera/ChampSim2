## 1. LTO for the fast build (Step A)

**Issue.** Link-time optimization had never been tried. Experiments 9 and 10 of the source
campaign did by hand the cross-file inlining LTO does automatically, and each helped some
traces while hurting others.

**Fix.** An opt-in `LTO=1` for fast. It adds `-flto=auto` to the fast policy's compile
options, which module objects also receive, and appends the mode's `-O3 -g3` plus
`-flto=auto` to the link options. The link needs them repeated because link-time
optimization sees none of the compile options, and user flags may not carry `-O` or `-g`.
The switch is part of the policy key and is recorded as `lto` in `--build-info`. With
`LTO=0`, every mode's compile, link and library options were checked identical to
`350e4e4e`'s.

**Files touched.** `Makefile`, `config/build_rules.mk`, `config/build_config.py`.

**Commit.** `bb636968` (`config: add an opt-in LTO=1 switch for the fast build`).

**Build checks.** Every object, module objects included, carries `.gnu.lto_*` sections;
the binary has 23 `GNU GIMPLE 13.3.0` code-generation units, keeps its debug sections, and
is 33.8 MB against the baseline's 44.7 MB. The link printed no warnings, `-Wodr` and
`-Wlto-type-mismatch` included. The whole build took 6.9 s (−j16, 80 s user). The linker is
GNU ld 2.42 (BFD) with GCC's `liblto_plugin.so`, GCC's default.

**Result: a split.**

| Trace | Before | After | Change | Pairs |
|---|---|---|---|---|
| sqlite | 448.74 (448.24–450.39) | 469.43 (467.88–471.60) | +4.61% | +4.71, +4.27, +4.73 |
| omnetpp | 446.42 (442.04–446.78) | 459.87 (459.30–461.71) | +3.01% | +2.89, +2.93, +4.45 |
| gcc | 536.87 (533.55–536.99) | 558.28 (557.26–561.48) | +3.99% | +4.58, +4.63, +3.78 |
| mcf | 182.70 (181.33–183.06) | 151.34 (150.78–152.57) | **−17.16%** | −16.54, −16.49, −17.64 |

Complete parity on the four traces and on all 12 overlay runs. During this gate's mcf
phase I ran a sub-second `g++` test link, which broke the no-overlap rule. mcf's three
pairs are consistent, so it had no visible effect.

**Diagnosis of the mcf loss.** `perf stat` on mcf (baseline → LTO): cycles 398.0 G →
485.2 G, instructions +4.2%, branches −7%. Instruction-cache, data-cache, TLB and
branch-miss counts all stayed within 3%, so it was neither misses nor front end.
`perf record` put it in `DRAM_ADDRESS_MAPPING::swizzle_bits`: 10.72% → 24.02% of cycles,
42.7 G → 116.5 G, about 85% of the loss. Symbol attribution moved between two profiles of
the same binary, but raw sample addresses showed 27% of all samples on a single
instruction, in an out-of-line constructor LTO had created:

```
1111fd: mov    %rsi,(%rsp)        ; 8-byte store
111205: mov    %rdx,0x8(%rsp)     ; 8-byte store
11120f: movdqa (%rsp),%xmm0       ; 16-byte load spanning both stores
111214: mov    %r8,%rcx           ; ← 65,693 samples (one instruction of skid)
```

With the whole program in one unit, GCC stopped inlining
`address_slice(extent_type, const address_slice<OTHER_EXT>&)` (`inc/address.h`) into
`swizzle_bits`. Out of line, the constructor copied its 16-byte `dynamic_extent` argument
through the stack, and a load spanning two stores cannot be store-forwarded. Zen's
store-to-load interlock counter, `ls_bad_status2.stli_other`, confirms it: 2.25 G → 14.25 G,
about 7 extra cycles for each extra interlock. The v2 traces spend far less time in legacy
DRAM mapping, so their LTO gain outweighed the loss.

Evidence: `$E/01-fast-lto/{build.log,champsim*,build-info.json,timing/,overlay-parity/,diagnosis-mcf/}`,
the last holding the `perf stat`, `perf record` and interlock data and the annotated
disassembly.

## 3. Move `address_slice`'s bound-check throws out of line

paths. That made them large enough that GCC under LTO stopped inlining one into
`swizzle_bits` (section 1).

local 18, and it wants to break that pattern differently: it reports the same complaint for
`champsim_assert.h` in master, so either spelling would have drawn a bot commit. The
standard-attribute spelling is clean under 13.

first attempt adding a stray space.

**Files touched.** `config/build_rules.mk`, `config/build_config.py`.

**Commit.** `25561e48` (`config: compile the C++20 Ramulator driver without LTO`).

## 5. `447-perfect-tlb` under LTO: a test-build initialization-order bug

**Issue.** Every LTO *test* build failed `447-perfect-tlb.cc:156`: the perfect STLB counted
3 LOAD hits where 2 are expected.

| Test build | 447 |
|---|---|
| release, fast | pass |
| fast+LTO, with or without the section 3 fix | fail |
| release+LTO (`CXXFLAGS=-flto=auto`) | fail, no assertion fires |
| fast+LTO under ASan+UBSan | fail; only the known ITTAGE shift and a leak summary reported |

A `-DDEBUG_PRINT` trace of the scenario showed every set index as 0 under LTO. gdb showed
`OFFSET_BITS` 0 in every cache the test built (12 and 6 without LTO), with `NUM_SET` and
`NUM_WAY` correct. With a zero offset, sets come from the lowest address bits, and DTLB
tags stop ignoring the page offset. So the revisit of the first page missed the DTLB and
reached the STLB a third time.

**Cause.** `src/main.cc` computed `LOG2_BLOCK_SIZE = lg2(BLOCK_SIZE)` and likewise for
the page size. The simulator build defines `BLOCK_SIZE` and `PAGE_SIZE` as constants in
that same file, so there `LOG2_*` are constant-initialized: `R` in `nm`. A test build
defines them in `test/cpp/src/000-test-main.cc` instead. There `main.cc` sees only the
`extern` declarations, so `LOG2_*` were dynamically initialized: `B` in `nm`, set by
`_GLOBAL__sub_I_LOG2_BLOCK_SIZE`. `defaults.hpp`'s namespace-scope builders are dynamically
initialized in every file that includes the header, and read `LOG2_*` for their offset
bits, so a builder whose initializer ran first read 0. The ordinary link happened to run
`main.cc`'s initializer first; LTO changed the order.

**Why the gates never saw it.** They compare simulator binaries, where `LOG2_*` are
constants, so initialization order cannot matter. gdb shows identical geometry in the
baseline (00), the unfixed LTO binary (01) and LTO+fix (05) for every cache (DTLB 32×4 at
12 bits, L1D 64×12 at 6, and so on), with identical `try_hit` counts. A set-index collapse
there would have changed nearly every statistic. Every test that builds caches from the
default builders ran with zero offset bits under LTO, yet only 447 failed. So the unit
suite would mostly not catch a set-index bug.

**Fix.** `LOG2_*` are now computed from `champsim::defs::block_size`/`page_size`, the
constants both definitions of `BLOCK_SIZE`/`PAGE_SIZE` use. They are constant-initialized
in every build, and their values are unchanged. New test 448 builds a `CACHE` from each
default cache builder in its own file, whose copies were initialized before `main()`, and
checks the offset bits. With the fix reverted it fails under fast+LTO (`0 == 12`,
`0 == 6`); with the fix it passes.

**Files touched.** `src/main.cc`, `test/cpp/src/448-default-builder-geometry.cc`.

**Commits.** `7939ce42` (`sim: constant-initialize LOG2_BLOCK_SIZE and LOG2_PAGE_SIZE`),
`7de1ba92` (`test: pin the default cache builders' offset bits`).

**Regression verdict.** Before 448 existed, the full suite passed in release, fast,
release+LTO and fast+LTO test builds (952 passed, 20 skipped each). With 448 it passes
in release and fast+LTO (953 passed, 20 skipped). The simulator is unchanged:
complete parity between the tree at `LTO=0` and PR #6's binary on the four traces and 12
overlay runs. GCC 9.5 and Clang 12 accept the change.

Evidence: `$E/2a-perfect-tlb/`: the traces, the gdb scripts, the before/after test
logs, and `sim-parity/` and `sim-overlay-parity/`.

## 6. Make LTO the default for fast under GCC

**Decision (user, 2026-09-27).** LTO becomes the default for fast builds, with GCC only.
The Clang question is answered with measurements:

| Compiler | `-flto=auto` | `-flto` / `-flto=thin` |
|---|---|---|
| GCC 13.3, GCC 9.5 (conda-forge) | links and runs | — |
| Clang 12 (conda-forge) | rejected: `unsupported argument 'auto' to option 'flto='` | link fails |
| Clang 15 (conda-forge) | accepted; link fails | link fails |

Every Clang link failed loading `LLVMgold.so`. Clang's bitcode objects link only through
that plugin or `lld`, and this host has neither. Clang+LTO also has no parity or timing
evidence. CI's compiler matrix builds only release mode, so it is unaffected either way.

**Fix.** `LTO` now defaults to `auto`: on for fast with GCC, off otherwise. `LTO=0` turns
it off. `LTO=1` insists, and is refused outside fast or with Clang
(`LTO=1 is validated only with GCC`). The helper tells GCC from Clang by the predefined
macros and reports the effective setting to Make as a fourth `inspect` word, because the
driver's `-fno-lto` must follow the resolved policy rather than the `LTO` variable.
`CLAUDE.md` no longer says assertions are the only fast/release difference, and
`tools/perf/README.md` documents LTO and `--dram-model`.

**Files touched.** `Makefile`, `config/build_config.py`, `config/build_rules.mk`,
`test/python/test_build_modes.py`, `CLAUDE.md`, `tools/perf/README.md`.

**Commit.** `b461d75e` (`config: build fast with LTO by default under GCC`).

**Regression verdict.**
- The resolved options for release, debug, fast `LTO=0` and fast `auto` equal the
  previous release, debug, fast, and fast `LTO=1` policies.
- `make fast` yields `lto: true` with 23 LTRANS units, and complete parity against the
  measured fast+LTO binary (09) on the four traces.
- The native driver gets `-fno-lto` only in fast.
- `make test`: 973 cases, 953 passed, 20 skipped. `make pytest`: 155 OK, 10 skipped (8
  native, 2 `clang++`).
- `test_build_modes` pins the default, the opt-out, the refusals and Clang's behaviour.
  Its Clang test skips without `clang++` and passes against conda Clang 12.

The measured effect of the new default is section 3's second table (legacy) and section
4's (native). Those were measured with `LTO=1`, which produces the same policy.

Evidence: `$E/12-lto-default/`.

## 9. Where the allocations come from

A scratch interposer (`$E/14-alloc-sources/malloc_sites.c`) sampled a backtrace on every
4096th allocation, symbolized with `addr2line -i`. Shares are of allocations
(sqlite / mcf):

- **Instructions built from the trace** (`instruction.h:166-167`, their register vectors):
  about 22% / 19%.
- **Instructions copied** in `O3_CPU::decode_instruction`: about 14% / 11%. Its
  `std::merge` into `std::back_inserter(DISPATCH_BUFFER)` copy-constructs every
  instruction, allocating its vectors afresh, then erases the originals. Merging through
  `std::make_move_iterator` would move them instead.
- **`std::deque` storage** for each pipeline stage and the trace reader: about 21% / 18%.
- **Per-packet vector copies** (`instr_depend_on_me`, `to_return`) in
  `CACHE::initiate_tag_check`, `channel::request`, `fill_type` and `try_hit`: about
  13% / 26%.

With tcmalloc, the allocator's own functions fall to 1.3–2.0% of samples. So removing
these at the source would add a few percent at most on top of tcmalloc, plus whatever
locality it brings.

Sections 10 and 11 remove the copies. The other three sources are staged in
`OPTIMIZATION.md`.

## 10. Move instructions into the dispatch buffer

**Issue.** `O3_CPU::decode_instruction` merged the decode and DIB-hit buffers into
`DISPATCH_BUFFER` with `std::merge` over plain iterators. That copy-constructed every
instruction, reallocating its operand vectors, and then erased both source ranges. This was
section 9's second-largest single source.

**Fix.** Merge through `std::make_move_iterator`. Nothing references an instruction before
dispatch (`registers_instrs_depend_on_me` is filled at scheduling), and `ooo_model_instr`'s
implicit moves are `noexcept`. **Commit** `cacc5bac`.

## 11. Move request and response packets instead of copying them

**Issue.** Every copy of a channel request, tag lookup, fill or response copies
`instr_depend_on_me`, and a fill also copies `to_return`. Many copies were of objects about
to be discarded:
- `channel::do_add_queue` copied each packet twice, and `add_pq` three times;
- the response constructor copied its by-value list;
- `initiate_tag_check` copied entries that `transform_while_n` then erases;
- `handle_miss` built both a fill and a forwarded request before knowing which it needed;
- `fill_type::merge` copied its survivor and the merged lists.

**Fix.** Forward or move at each of those sites. `add_rq`/`add_wq`/`add_pq` gain `&&`
overloads that move only when the packet is accepted, so a rejected packet stays intact for
its retry. `merge` captures the fields it reads before moving its operand. The writeback,
translation, page-walk and core data-bus enqueues pass their packets on at their last use.
**Commit** `754b2397`.

**Allocations** per simulated instruction (glibc build): sqlite 9.96 → 8.55 (−14.2%), mcf
12.96 → 10.04 (−22.5%). With section 10, that is −26.7% and −31.0% from the start of the
day.
